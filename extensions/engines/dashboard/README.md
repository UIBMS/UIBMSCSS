# Optional dashboard layout extension

Development candidate; MIT. Load only the modules you need after UIBMSCSS. No runtime dependency, router, data model or visual framework is imposed. The released CSS bundles are unchanged.

## App Shell

Load app-shell.css, sidebar.css and topbar.css. Use .app-shell with direct header, labelled nav and main children. An embedded workspace can use a labelled section. Existing .app-shell-grid markup with .dashboard-topbar, .dashboard-sidebar and .dashboard-workspace regions is supported. The desktop button.sidebar-toggle controls the uniquely identified sidebar with aria-controls and aria-expanded. Import mountAppShell(shell,{expanded:true,mobileExpanded:false}) for independent navigation state and the desktop icon rail. For the optional icon rail, put an aria-hidden SVG and a span with the accessible link text directly inside each link or summary. CSS determines whether the container is wide (42rem or more) or compact.

For mobile drawers, also load components/drawer.css and add a direct dialog.drawer.drawer-start.dashboard-nav-drawer inside the shell (inside .app-shell-grid for existing markup). Author an accessible title and a native method="dialog" close form in the dialog. In the topbar add button.sidebar-drawer-toggle with commandfor targeting the dialog, command="show-modal" and aria-haspopup="dialog". Mount the existing mountDrawers(document) adapter only if native command or backdrop compatibility is required. The App Shell moves the existing sidebar into this authored native dialog in compact mode and restores it to the grid in wide mode. It never clones the navigation or calculates CSS dimensions. Modal focus isolation, Escape, backdrop dismissal (when closedby="any"), and focus return remain browser-owned. Native links close the drawer on unmodified selection; nested details retain their state. Resizing to wide closes an active modal. Existing markup without a mobile dialog retains its in-flow compact disclosure as a compatibility path. Without the shell controller, the sidebar remains visible in-flow and both toggle buttons are hidden.

setExpanded(value), refresh(), mode, expanded and destroy() remain available; sidebarvisibilitychange reports native modal or rail state. --dashboard-height (100dvh), --dashboard-sidebar-width (15rem), --dashboard-rail-width (by default max(4rem, target size + both sidebar padding edges + border)), --dashboard-content-padding (var(--space)), --dashboard-mobile-drawer-width (24rem), and the legacy --dashboard-mobile-nav-height (14rem) configure layout. Use a definite height for independent desktop scrolling. No routing, persistence or global application state is imposed.

## Sidebar

Load sidebar.css. Use a labelled nav under .app-shell with native lists, links and details/summary for nested groups. For a standalone sidebar, use nav.dashboard-sidebar directly. The older aside.dashboard-sidebar with nav.sidebar-nav remains supported. Mark the current link with aria-current="page"; only the application chooses the active route. Sidebar background/foreground can be customized using --dashboard-sidebar-background and --dashboard-sidebar-foreground. The full link name is preserved in the collapsed shell.

## Topbar

Load topbar.css. A direct header in .app-shell or .dashboard-topbar accepts ordinary native headings, search, buttons and links. When grouping branding and actions, use two direct div children in that order; no group classes are required. The explicit .topbar-brand and .topbar-actions hooks remain supported. Groups wrap at narrow widths. Use existing independently loadable dropdown, drawer, toast and command palette extensions when needed.

## Page header

Load page-header.css. Use .dashboard-page-header on a native header containing a direct div with the heading and description, optionally followed by a second div with actions. A labelled nav with a native ordered list in the heading group provides breadcrumbs. The older .page-heading, .page-actions and .dashboard-breadcrumb hooks remain supported. Actions wrap without a required icon set or placement policy.

## Split workspace

Load split-workspace.css. Use two pane elements such as sections, with a labelled element carrying role="separator" between them, directly inside .split-workspace. No grid wrapper or pane classes are required. The older .split-workspace-grid wrapper and .split-pane/.split-handle classes remain supported. Give the handle an accessible name, aria-controls pointing to the primary pane, and tabindex="-1" before mounting. Import mountSplitWorkspace(root,{ratio:.42,minStart:160,minEnd:220,keyboardStep:.05}) from split-workspace.mjs. Pointer drag uses pointer capture; Left/Right and Home/End adjust the split with logical RTL support. Limits are computed from actual available width; the ratio is preserved when the container stacks below 36rem. The handle is hidden in stacked mode. Without JS, panels retain a static ratio and the handle is hidden. setRatio(value), ratio, refresh() and destroy() are available; splitresize reports the applied ratio. Use --dashboard-split-ratio and --dashboard-split-gutter to customize defaults. This is a layout component, not a record editor or drag-and-drop data engine.

All five structures inherit appearance tokens. Layout-defining shell, sidebar, topbar, workspace and splitter boundaries stay stable when Liquid Silicone is enabled; nested ordinary surfaces, navigation selection and native controls retain material feedback. Browser and accessibility certification remain outstanding.

## Widget components

The six widget patterns share core surfaces and layouts; none duplicates a card, panel, button, reset, palette or typography engine.

- KPI and statistic cards: Apply .metric-card to a dl with a dt for its label and a dd for the value. Compose it with the existing .card/.panel and .stack. A strong inside dd can emphasize the value when the metric has supporting content. For statistic articles, direct strong and small children represent the headline and supporting text. Use a direct span with data-tone inside a metric article or its description-list value for semantic change emphasis. No dedicated child classes are needed; existing .metric-label, .metric-value, .metric-context and .metric-change hooks remain supported. Application data and formatted values stay in HTML. Always provide descriptive text. --dashboard-metric-size adjusts the metric headline. Use native progress, meter, lists and description lists for measurements.
- Widget grid: widget-grid.css extends .grid.widget-grid with --dashboard-widget-min (16rem default) and --dashboard-widget-gap (existing --space default). The existing grid provides display and auto-fit behavior; no JS, dragging or persistence.
- Quick actions: quick-actions.css adds text wrapping/alignment to a .cluster or .stack of native links/buttons. Application routing and action handlers remain external.
- Sparklines: sparkline.css styles native SVG marks via currentColor and existing accent role. Static SVG can be authored directly as a child of figure.sparkline. For dynamic series, mountSparkline(figure) from sparkline.mjs reads native data[value] elements inside details > ol > li and generates geometry in the initially empty direct SVG child. Legacy .sparkline-plot and .sparkline-values hooks remain supported. Use a visible caption and accessible actual observations, for example an expandable ordered list. refresh() reads updated values; destroy() restores authored attributes. sparklinePoints(values,{width,height,padding}) is pure and rejects nonfinite data. Individual series normalize to their own range. Customize --dashboard-sparkline-height, --dashboard-sparkline-ink, --dashboard-chart-stroke.
- Progress rings: progress-ring.css plus optional mountProgressRing(root,{format}) from progress-ring.mjs. A direct native progress child owns value, max and accessible name. The ring and localized readout are decorative; the original control remains accessible. Changes to value/max synchronize automatically. Indeterminate progress and no-script fallback remain native. refresh() and destroy() manage lifecycle. Customize --dashboard-ring-size, --dashboard-ring-stroke, --dashboard-ring-ink and --dashboard-ring-value-size.

## Engineering conventions

Reuse the existing semantic HTML styling, layout classes, contextual design profiles, shared colour roles, motion and accessibility preferences before creating new CSS. Prefer one meaningful component class and native internal markup; use contextual CSS nesting with low specificity instead of styling each child with a class. Add only component-specific structure; use meaningful CSS custom properties where developers need configuration, rather than creating tokens for every literal. No fixed component colour palette, embedded business data, application routes or mandatory runtime. Geometry constants, native CSS keywords and documented defaults are valid implementation details. Keep sample data and demo-specific routing in documentation. Each Dashboard catalogue entry owns its stylesheet dependencies; the renderer reads that metadata. Native controls are authoritative, and optional scripts consume actual data/markup. Maintain browser and accessibility verification gates; do not treat a static render as full browser certification.

## Derived geometry (GEO-002)

The default collapsed rail derives its width from the shared shell/sidebar inset and target size, not a separate fixed width. An explicit rail-width override remains authoritative. Unsized decorative SVG icons in native sidebar and metric-label markup follow the local line height; legacy sidebar icon hooks remain supported. Splitter gutter and grip dimensions respond to density and border width while the existing keyboard/pointer adapter owns the ratio. The optional ring stylesheet normalizes the existing numeric or length-valued stroke using two private registered properties and calculates the radius from its 100-unit viewBox (4-unit clearance); unsupported arithmetic retains the original SVG geometry. Sparkline height responds to larger line height, with the existing explicit height override and coordinate-generation algorithm preserved. See [GEO-002](../../../docs/ARCHITECTURE.md#geo-002--mathematically-derived-contextual-geometry).
